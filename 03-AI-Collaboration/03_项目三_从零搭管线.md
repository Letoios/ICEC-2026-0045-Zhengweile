# 03 · 项目三：在「什么都没有」的机器上搭声学管线

项目三要做「用手机麦克风采电风扇声音，靠频谱特征判断工况」。
开工第一天遇到的第一件事不是算法，是**这台电脑上什么都没有**。

这一篇记五个节点。

---

## 案 1｜没有 scipy、没有 librosa、连 ffmpeg 都装不上

**问题**：环境检查发现：

```
numpy 2.3.5 ✓   pandas 3.0.1 ✓
scipy ✗   soundfile ✗   librosa ✗   ffmpeg ✗
```

手头只有手机录的 **mp3**。没有解码器 = 一步都走不了。

**尝试过的路（都失败）**：
1. `pip install imageio-ffmpeg` → `Errno 13: Permission denied: '...pip-unpack-...whl.metadata'`；
2. 换 `--target D:\deepseek工作\.pylibs` → 同样权限错；
3. 换 `$env:TEMP` 到工作区 → 同样；
4. 用 `urllib` 直接下 wheel → 下载到一个后台任务里，超时。

**我的提问**：「装不上包，是不是只能放弃 mp3、让用户重录成 wav？」

**AI 的回答**：先别放弃。系统里可能已经有 ffmpeg 的**动态库** ——
Electron 系的应用经常自带 `ffmpeg.dll`。搜一下。

**我做的验证**：`Get-ChildItem -Recurse -Filter ffmpeg.dll` → 找到 `D:\deepseek\ffmpeg.dll`（3.1 MB）。

然后写 `code/mp3read.py`，**用 ctypes 直接调 libavcodec**：

```python
lib = ctypes.CDLL(r"D:\deepseek\ffmpeg.dll")
lib.avcodec_find_decoder.restype = ctypes.c_void_p
...
```

**踩的坑**：

| 现象 | 根因 | 修法 |
|---|---|---|
| 峰值读出来是 `nan`、时长只有 4.30 s | 把 int16 平面（`AV_SAMPLE_FMT_S16P`=6）当成 float32 读 | 按 `format` 分支：`fmt in (6,7)` 走 int16 `/32768`，否则 float32 |
| 帧长算错 | 以为码率 128 kbps，实际 320 kbps | 按帧头解析：`144*bitrate/samplerate + padding` |
| `AVFrame` 字段读不到 | 结构体定义不完整 | `data[8]` 在偏移 0，`nb_samples` 在偏移 112，`format` 在 116，用 `ctypes.cast(fr, POINTER(c_int))[28]/[29]` 读 |

**结论**：**98 段录音全部解码成功，0 失败。**
`ffmpeg.dll` 没有 `av_parser_init` / `swr_convert`，所以帧切分和重采样都自己写 ——
反而比调包更清楚中间发生了什么。

## 案 2｜f0 用「最大峰」估，同一个文件换窗长就换答案

**问题**：第一段真实录音（4.3 s，一档）算基频：
15–200 Hz 内 **46.88 Hz（幅值 0.00438）** 和 **29.30 Hz（幅值 0.00424）** 几乎等高，
`argmax` 在两者之间摇摆；同一个文件换 FFT 长度，答案就变。

**我的提问**：「f0 到底取哪个？差 60% 呢。」

**AI 的回答**：取最大峰这个方法本身就不对。
风扇是**谐波信号** —— 真正的基频会让 **2f0、3f0、4f0… 都落在强峰上**。
用「谐波梳」：让 `k*f0 (k=1..6)` 的谱线能量和最大，高次权重 `1/k`。

**我做的验证**：写了 `estimate_f0(freqs, amp, lo=15, hi=120, kmax=6, step=0.02)`，
分辨率到 0.02 Hz。合成样本测试：真值 25 / 45 Hz，估出 **25.0 / 45.1**。

**结论**：谐波梳成了默认方法。
但后来发现 —— **转速本身在这套数据上不可靠**（见案 3），
f0 最终只当「辅助说明」，判档位用的是谱形。

## 案 3｜五分类崩到 43.2%：我一直以为可分的那条线是假的

**背景**：早期用三个干净样本（一档 / 三档 / 五档各一段）测出「谱心 90–106 / 128–166 / 172–190，完全分得开」，
我当时把这个结论写进了采集作业书。

**问题**：补到 95 段之后，用同样的特征做五分类留一法 → **43.2%**（随机是 20%）。
混淆集中在 C1↔C3、C2↔C1。

**我的提问**：「95 段了反而更差？是不是代码错了？」

**AI 的回答**：先看组内离散度，再看组间差。

**我做的验证**：

- 组内谱心范围 **372–1366 Hz（3.7 倍）**；
- 组间中位数只差 **50–100 Hz**（658 / 757 / 708）。

**组内比组间大一个数量级。**

**结论**：谱心主要反映**手机摆在哪、离多远**，不是档位。
之前那个「完全分得开」是**从 3 个样本里看出来的假象** —— 而每个档位只录了一段，位置当然不同。

**改法**：
1. 换 f0（谐波梳）→ 五类提到 56.8%；
2. 加 h2/h3/h4 谐波比 + kNN → 66.3%；
3. **把问题定义从「识别 5 个档位」改成「识别正常 / 失衡 / 遮挡」→ 90.8%**。

第 3 条是真正的转折：**不是模型变好了，是问题问对了。**
档位差 20%，误差也差不多 20%；故障差 2–6 倍，误差盖不住。

落到 `proj03/docs/方法说明.md` §4、`docs/档位与工况说明.md`。

## 案 4｜抗噪跑出「五类 0.0%」

**问题**：第一版抗噪脚本给每个 SNR 都算出一个准确率，其中五类全是 0.0%。

**我的提问**：「0% 不可能，肯定是 bug。」

**AI 的回答**：看分组键。你的分组交叉验证按批次留出，如果批次键取错了，所有样本会落到同一个批次。

**我做的验证**：确实是 ——
批次字符串用了 `m["file"]`，而 `file_map.json` 里根本没有这个键，取出来全是 `None` → 全归一个批次 → 留出后训练集空。

还有第二个问题：抗噪脚本的特征算法和 `featurize.py` **不是同一套**（FFT 长度不同），
导致三类只有 84.6%（应该是 90.8%）。

**改法**：批次从 `os.path.basename(m["path"])` 里的 `_(\d+)\.` 解析；
特征算法与 `featurize.py` 完全统一（频段用 16384 点、f0 用 65536 点）。

**重跑后的抗噪表（分组 CV）**：

| SNR | 无噪 | 30 | 20 | 15 | 10 | 5 dB |
|---|---|---|---|---|---|---|
| 三类 | 90.8 | 89.8 | 89.8 | 86.7 | 82.7 | **79.6** |
| 五类 | 60.2 | 58.2 | 58.2 | 51.0 | 52.0 | 51.0 |

**结论**：三类抗噪相当好（掉 11 个点）；五类在 51–60% 之间平着走 ——
**加噪没让它更差，说明瓶颈不是噪声，是档位本身分不开。**
这个「负面结果」反而是最好的一条论据。

## 案 5｜我预测规则会接近 90%，实测 82.7%

**问题**：为了回答「为什么不用纯阈值规则」，我写了一版手写阈值树，并预测：

> 「规则在三类上应该也接近 90%，只是样本少时不如 kNN 稳。」

**结果**：先用中位数中点当阈值 → 三类只有 **73.5%**。
再用网格搜索找**最优**阈值（h2 1.5–6.0 步长 0.1、e_high 0.15–0.26 步长 0.005、f0 扫 0.1 Hz）→ **82.7%**。

而 kNN 是 **90.8%**。

**关键点**：规则阈值是**在含测试样本的全量数据上扫出来的**（等于偷看了答案），
kNN 是零参数、没调过。**规则占了便宜，还是输 8 个点。**

**结论**：我原来的预测是错的，而且错得很自然 ——
是因为「手写规则听起来更可解释，所以应该差不多」这个直觉本身就不对。

真实原因是：**故障的边界不是轴对齐的**。
「高频占比 > 0.26 就是失衡」这类矩形切分，切不开一个斜着分布的两类点。
kNN 不假设形状，所以赢。

**这条写进了报告**：选 kNN 不是因为「别的不会」，是**对比过、量化过**。
落到 `proj03/docs/创新点.md` 创新一、`results/rules_vs_ml.json`。
